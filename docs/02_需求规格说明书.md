# 1．引言

## 1.1 编写目的

为明确"智能共享自习室预约系统"的软件需求、安排项目规划与进度、组织软件开发与测试，特编写本需求规格说明书。

本文档的预期读者为：项目经理（组长）、系统设计与开发人员、测试人员以及课程设计指导教师。本文档将作为系统概要设计、详细设计、测试计划编制的输入，以及最终系统验收的依据之一。

## 1.2 项目背景

a. **委托单位、开发单位与主管部门**：本项目为《系统分析与设计》课程设计课题，由课程设计小组（5 人）自主选题、自主开发，指导教师所在课程组为业务主管部门。

b. **系统与其他系统的关系**：本系统为独立 B/S 架构 Web 应用，不依赖外部业务系统；对外仅依赖标准网络与浏览器环境。系统面向高校共享自习室场景，向前来自习的学生提供座位查询、预约、签到等服务，向管理员提供座位资源管理与运营统计服务。

**现状与问题**：调研发现，传统自习室管理存在以下痛点——

1. **信息不透明**：学生无法提前得知自习室空位情况，往返奔波"找座"时间成本高；
2. **占座严重**：物品占座导致座位名义占用、实际闲置，资源利用率低；
3. **爽约无成本**：预约后不到场没有任何约束，座位被无效锁定；
4. **管理粗放**：管理员缺乏数据支撑，无法量化了解各时段、各区域的座位利用情况；
5. **分配低效**：高峰期人工引导分配座位秩序混乱，体验差。

本系统通过"在线选座 + 智能分配 + 信用治理 + 数据可视化"四位一体的方案解决上述问题。

## 1.3 定义

| 术语/缩写 | 说明 |
| --- | --- |
| JWT | JSON Web Token，无状态令牌式身份认证方案 |
| RBAC | Role-Based Access Control，基于角色的访问控制 |
| bcrypt | 自适应密码哈希算法，用于口令存储 |
| DFD | Data Flow Diagram，数据流图 |
| ER 图 | Entity-Relationship Diagram，实体联系图 |
| 座位热力图 | 以颜色深浅表达"座位 × 时段"利用率矩阵的可视化图表 |
| 候补队列 | 目标时段满座时按先到先得排队的等待机制 |

# 2．任务概述

## 2.1 目标

**总体目标**：建设一套面向高校共享自习室的智能座位预约与管理平台，实现座位资源的在线化、公平化、数据化管理，提升座位利用率与学生自习体验。

**具体目标**：

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | 在线预约 | 学生可按日期、时段、自习室在线选座预约，杜绝盲目找座 |
| G2 | 智能分配 | 系统按用户偏好（区域/电源/靠窗）自动推荐并分配最优座位 |
| G3 | 全生命周期管理 | 预约"待签到→签到→使用→签退"全流程线上化，超时自动违约处理 |
| G4 | 信用治理 | 违约扣分、履约加分、低分限约，从机制上抑制爽约与占座 |
| G5 | 满座候补 | 目标时段满座时可排队候补，空位释放自动递补并通知 |
| G6 | 数据可视化 | 提供座位热力图、使用率趋势、高峰时段等运营统计 |
| G7 | 消息通知 | 预约成功、违约警告、候补递补等关键事件站内通知 |

## 2.2 运行环境

**服务端**：

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Linux（本项目在 WSL2/Arch Linux 环境开发验证） |
| 运行时 | Go 1.27 + Gin Web 框架 |
| 数据库 | PostgreSQL 18（库名 studyroom，启用 btree_gist 扩展） |
| 硬件建议 | 2 核 CPU / 2GB 内存及以上 |

**客户端**：

| 项目 | 要求 |
| --- | --- |
| 浏览器 | Chrome / Edge / Firefox 等现代浏览器最新两个大版本 |
| 分辨率 | 1366×768 及以上，支持响应式布局 |

**开发环境与完整技术栈**：后端采用 Go 1.27、Gin 1.12.0、pgx 5.10.0、golang-jwt 5.3.1、go-redis 9.22.0 与 bcrypt（单测另用 miniredis 提供内存 Redis 替身）；主数据存储为 PostgreSQL 18，Redis 7 用于缓存、限流、JWT 注销黑名单和分布式协调。前端采用 Vue 3.5.42、Vite 8.2.2、Vue Router 5.3.0、Pinia 4.0.3、Element Plus 2.14.5、Axios 1.20.0、ECharts 6.1.0、GSAP 3.15.0 与 Three.js 0.185.1（3D 座位探索视图）。AI 助手通过 OpenAI Chat Completions 兼容接口接入，需支持 SSE 流式输出与 tools/function calling。系统通过 Docker Compose 编排 PostgreSQL、Redis 和后端服务。

## 2.3 条件与限制

1. **进度约束**：课程计划周期为 2026-09-01 至 2026-09-15，包含分析、设计、实现、验证和答辩交付；
2. **人力约束**：5 人课程设计小组，均为在校学生，非全职投入；
3. **范围约束**：教学演示系统，单校区单实例部署；不包含在线支付、门禁硬件对接、短信网关等外部集成；
4. **技术约束**：预约时间粒度为 30 分钟；单日单座可被多次预约但时段不得重叠；系统时间以服务器时间为准；
5. **合规约束**：用户口令必须加密存储，日志不得输出明文口令。

## 3.3 数据库介绍

采用 **PostgreSQL 18** 关系数据库，库名 `studyroom`，启用 `btree_gist` 扩展以支持时段排他约束。共 9 张核心表：`users`（用户）、`rooms`（自习室）、`seats`（座位）、`reservations`（预约）、`credit_logs`（信用流水）、`waitlist`（候补）、`notifications`（通知）7 张业务表，以及 AI 助手专用的 `ai_conversations`（会话）与 `ai_messages`（消息）2 张表（由迁移脚本 `002_ai_assistant.sql` 建立）。

## 3.4 数据词典

**（1）users 用户表**

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| id | BIGSERIAL | 主键 | 用户标识 |
| username | VARCHAR(50) | 唯一、非空 | 登录名 |
| password_hash | VARCHAR(100) | 非空 | bcrypt 口令哈希 |
| real_name | VARCHAR(50) | — | 真实姓名 |
| student_no | VARCHAR(20) | 唯一 | 学号 |
| role | VARCHAR(20) | student/admin | 角色 |
| credit_score | INTEGER | 0–100，默认 100 | 信用分 |
| credit_banned_until | TIMESTAMPTZ | 可空 | 低分禁约截止时间 |
| status | VARCHAR(20) | active/disabled | 账号状态 |
| created_at / updated_at | TIMESTAMPTZ | 非空 | 创建/更新时间 |

**（2）rooms 自习室表**

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| id | BIGSERIAL | 主键 | 房间标识 |
| name | VARCHAR(100) | 唯一、非空 | 房间名称 |
| location | VARCHAR(200) | — | 位置描述 |
| open_time / close_time | TIME | close > open | 开放时段 |
| seat_rows / seat_cols | INTEGER | 1–30 | 平面图行列规模 |
| description | TEXT | — | 房间说明 |

**（3）seats 座位表**

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| id | BIGSERIAL | 主键 | 座位标识 |
| room_id | BIGINT | 外键→rooms，级联删除 | 所属房间 |
| seat_no | VARCHAR(20) | 房间内唯一 | 座位号（如 A01） |
| row_no / col_no | INTEGER | ≥1，(room,row,col) 唯一 | 平面图坐标 |
| zone | VARCHAR(30) | quiet/regular/discussion/computer | 功能区域 |
| has_power | BOOLEAN | 默认 false | 是否带电源 |
| near_window | BOOLEAN | 默认 false | 是否靠窗 |
| status | VARCHAR(20) | available/maintenance/disabled | 座位状态 |

**（4）reservations 预约表**

| 字段 | 类型 | 约束 | 含义 |
| --- | --- | --- | --- |
| id | BIGSERIAL | 主键 | 预约单标识 |
| user_id / seat_id | BIGINT | 外键，级联删除 | 所属用户/座位 |
| res_date | DATE | 非空 | 预约日期 |
| start_time / end_time | TIME | end > start | 起止时间 |
| status | VARCHAR(20) | 六态枚举 | 当前状态 |
| source | VARCHAR(20) | manual/auto/waitlist | 预约来源 |
| checkin_at / checkout_at / leave_at | TIMESTAMPTZ | 可空 | 签到/签退/离开时间戳 |
| — | 排除约束 | 见下 | 时段冲突防护 |

排除约束（数据库层兜底，双保险）：

- `excl_seat_overlap`：同一座位同一天的**活跃预约**时段不得重叠；
- `excl_user_overlap`：同一用户同一天的**活跃预约**时段不得重叠（防止一人多占）。

**（5）credit_logs 信用流水表**：id、user_id（外键）、delta（分值变动，正加负减）、reason（事由）、reservation_id（关联预约，可空）、created_at。

**（6）waitlist 候补表**：id、user_id、room_id、res_date、start_time/end_time、偏好（zone/has_power/near_window，均可空）、status（waiting/promoted/cancelled/expired）、created_at。同一房间同一时段按 created_at 先后排队。

**（7）notifications 通知表**：id、user_id、type（六类事件枚举）、title、content、is_read、created_at。

**（8）ai_conversations AI 会话表**：id、user_id（外键→users，级联删除）、title（默认"新对话"）、created_at、updated_at。索引 `(user_id, updated_at DESC)` 支撑会话列表按最近活跃排序。

**（9）ai_messages AI 消息表**：id、conversation_id（外键→ai_conversations，级联删除）、role（system/user/assistant/tool）、content、tool_calls（JSONB，兼容 OpenAI 工具调用）、tool_call_id、status（streaming/complete/failed）、created_at。索引 `(conversation_id, created_at, id)` 保证消息按序回放；仅 `complete` 状态消息进入后续模型上下文。

## 3.5 数据采集

1. **管理端录入**：房间与座位由管理员创建/批量生成，形成静态资源数据；
2. **用户注册采集**：注册时采集用户名、口令（哈希）、姓名、学号；
3. **行为自动记录**：预约创建、签到、签退、取消等操作由系统自动写入对应表并维护时间戳；
4. **调度器采集**：后台定时任务扫描超时未签到预约，自动产生违约记录与信用流水；
5. **统计聚合**：热力图与统计报表由历史预约数据按"座位 × 小时"聚合生成，无需人工上报。

# 4．功能需求

## AI 助手补充需求

| 编号 | 需求 |
| --- | --- |
| FR-11 | 学生可通过全局悬浮入口打开 AI 助手，以流式对话查询本人资料、信用、预约、候补和通知。 |
| FR-12 | 系统可将当前学生的业务数据、全部房间与座位一次性组织为模型上下文，每条用户消息最多调用一次兼容模型服务。 |

## 4.2 功能描述

### FR-01 用户注册

| 项目 | 内容 |
| --- | --- |
| 参与者 | 游客 |
| 前置条件 | 无 |
| 主流程 | 填写用户名/口令/姓名/学号 → 校验唯一性 → 口令 bcrypt 哈希后入库 → 注册成功 |
| 后置条件 | 生成 student 角色用户，信用分初始化为 100 |
| 异常 | 用户名或学号已存在（409）；口令强度不足（≥6 位） |

# 5．性能需求

## 5.1 数据精确度

| 数据 | 精确度要求 |
| --- | --- |
| 预约时间 | 粒度 30 分钟，起止时间精确到分钟 |

| 利用率统计 | 百分比，保留 1 位小数 |
| 时间基准 | 统一采用服务器时区（Asia/Shanghai） |

## 5.2 时间特性

以下数值是验收目标，尚未完成专项性能复测，不作为实测结果。（注：高并发抢座场景的实测数据见《系统测试报告》SSR-TEST-001 第 4 章。）

| 指标 | 要求 |
| --- | --- |
| 常规查询接口响应 | P95 < 300ms（本地网络） |
| 热力图/统计聚合接口 | P95 < 1s（14 天数据量） |
| 预约提交（含冲突检测） | P95 < 500ms |

# 7．其它需求

## 7.1 安全保密

1. 口令仅存 bcrypt 哈希（cost=10），任何接口/日志不得出现明文口令；
2. 会话采用 JWT（HS256，24 小时有效），签名密钥环境变量注入；登出时按令牌剩余有效期写入 Redis 黑名单，实现主动注销；
3. RBAC：管理端接口仅 admin 角色可访问；AI 助手接口仅 student 角色可访问，会话按 user_id 隔离；
4. 全部 SQL 采用参数化查询，防 SQL 注入；前端输入做长度与格式校验，防 XSS；
5. AI 接口的模型密钥、系统提示词与其他用户数据不得返回前端；日志不记录提示词和业务快照；
6. 敏感端点（登录、预约、自动分配、AI 对话）挂载 Redis 限流中间件，超阈值返回 429；
7. 当前开发配置允许任意来源，正式部署前应收紧为可信来源白名单。

## 7.2 可维护性

1. 后端按 handler / service / repository 三层组织，模块边界清晰；
2. 数据库变更通过迁移脚本管理（001_init.sql、002_ai_assistant.sql），可重复执行；
3. 关键业务（分配算法、时段校验、信用规则、缓存抖动、分布式锁、限流）配套单元测试，CI 自动执行；
4. 统一结构化日志，便于排障；Redis 不可用时按用途差异化降级。

## 7.3 可移植性

1. 后端为静态编译的 Go 程序，可部署于任意 Linux 环境，具备容器化条件；
2. 数据库采用标准 SQL 与 PostgreSQL 特性（排除约束），迁移成本可控；
3. 前端构建产物为静态资源，可由任意 Web 服务器托管；
4. 运行配置全部经环境变量注入（根目录 `.env` 统一维护），可在不同环境间迁移。

## 7.4 可使用性

1. 座位平面图直观呈现占用状态，另提供 3D 座位探索视图与偏好动效反馈，预约操作 ≤ 3 步；
2. 自动分配提供推荐理由，增强可解释性与信任感；
3. 关键结果（预约成功、违约、递补）均有即时消息反馈；
4. AI 助手支持自然语言查数与选座推荐，推荐结果必须二次确认，避免误操作。
