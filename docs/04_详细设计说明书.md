## 3.12 缓存与高并发协调架构（Redis 组件设计）

为了提升系统在高并发选座与热点查询场景下的吞吐能力并保障分布式一致性，系统新增独立的高性能内存协调层：

### 1. 分布式互斥锁组件（internal/pkg/redissync）
- **加锁实现**：基于 `redis.SetArgs{Mode: "NX", TTL: expire}` 命令。加锁时生成全局唯一的 UUID 作为 Token（Value）。若获取失败，直接返回不可重入互斥错误；
- **原子解锁**：采用 Lua 脚本比对 Token，确保仅有锁的持有者能够释放锁，杜绝因任务超时导致的误删他人锁问题：
  ```lua
  if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
  else
      return 0
  end
  ```
- **优雅降级**：当 Redis 客户端为 nil（未配置或离线降级）时，`TryLock` 自动放行返回虚拟解锁函数，确保系统在纯 PostgreSQL 模式下仍可继续工作。

### 2. 旁路缓存组件（internal/pkg/rediscache）
- **读取策略（Cache-Aside）**：先查 Redis。命中且反序列化成功则直接返回；未命中时触发 loader 回源查询数据库，并将结果以 JSON 格式写回 Redis；
- **防雪崩机制（Jitter）**：基础 TTL（如 5 分钟）额外叠加 `基础 TTL 的 ±10%` 随机抖动时间，打散同一批热点数据的过期时点；
- **主动失效**：数据发生变更（写操作）时，通过 `Delete` 或 `DeletePrefix` 立即剔除失效键，保证数据最终一致性。

### 3. API 频次限流中间件（internal/middleware/ratelimit.go）
- **算法模型**：固定窗口计数器模型。客户端发起请求时，以 `ratelimit:<prefix>:<identifier>` 为键执行 `INCR`；
- **原子初始化**：若计数器值为 1，则同时设置窗口过期时间（`EXPIRE window`）；
- **阻断控制**：若计数值超过上限，直接中断请求链并响应 HTTP 429 Too Many Requests，并输出规范的 `{"code": 429, "message": "请求过于频繁，请稍后再试"}`。

### 4. JWT 注销黑名单（internal/service/auth.go）
- 传统的无状态 JWT 无法提前注销。本系统在用户调用 `/api/auth/logout` 时，服务端解析 Token 的剩余生存时间（`exp - now`）；
- 将 Token 哈希值存入 Redis：`SET studyroom:auth:blacklist:<hash> "1" EX <remaining_seconds>`；
- `JWTMiddleware` 中间件在每次验证签名通过后，额外查询一次 Redis 黑名单，已注销的 Token 将被即时拦截，保障会话安全。
