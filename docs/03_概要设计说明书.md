# 1．引言

## 1.1 编写目的

本说明书依据《需求规格说明书》（SSR-REQ-001）编制，从总体上定义智能共享自习室预约系统的体系结构、模块划分、外部/内部接口、数据结构与运行方式，作为后续详细设计与编码工作的直接依据。

预期读者：系统设计与开发人员、测试人员、课程设计指导教师。

## 1.2 项目背景

a. 本项目为《系统分析与设计》课程设计课题，由 5 人项目小组自主选题开发，指导教师所在课程组为主管部门；

b. 本系统为独立 Web 应用（B/S 架构），通过浏览器向学生与管理员提供服务，不与其他业务系统存在接口依赖；数据库采用自管 PostgreSQL 实例。

## 1.3 定义

| 术语/缩写 | 说明 |
| --- | --- |
| 分层架构 | handler（HTTP 适配）→ service（业务）→ repository（数据访问）的三层组织方式 |
| 仓储模式 | Repository 模式，将数据访问细节封装在独立层 |
| 调度器 | 后台定时任务组件，负责违约扫描、候补递补、签到提醒 |
| 分布式锁 | 基于 Redis 实现的资源互斥锁，保障高并发预约与调度器主备选举 |
| Cache-Aside | 旁路缓存模式，先读缓存，失效查库并回填，数据更新时失效缓存 |
| DSN | Data Source Name，数据库连接串 |
| 迁移脚本 | 声明式 SQL 脚本，管理数据库结构演进 |
| 优雅降级 | Redis 离线时自动切换为纯数据库模式，核心功能持续可用 |
| 优雅关闭 | 收到终止信号后停止接收新请求、等待在途请求完成再退出 |

# 2．任务概述

## 2.1 目标

在需求规格说明书确定的 G1–G7 目标下，给出可实现的技术总体方案：前后端分离 + REST API + 关系数据库 + Redis 内存缓存/分布式锁 + 后台调度器，保证功能完整、结构清晰、并发安全且便于分工并行开发与测试。

## 2.2 运行环境

后端采用 Go 1.27、Gin 1.12.0、pgx 5.10.0、golang-jwt 5.3.1、go-redis 9.22.0 与 bcrypt；主数据存储为 PostgreSQL 18，Redis 7 用于缓存、限流、JWT 注销黑名单和分布式协调。前端采用 Vue 3.5.42、Vite 8.2.2、Vue Router 5.3.0、Pinia 4.0.3、Element Plus 2.14.5、Axios 1.20.0、ECharts 6.1.0、GSAP 3.15.0 与 Three.js 0.185.1。AI 助手经 OpenAI Chat Completions 兼容接口调用模型（需支持 SSE 流式与工具调用）。系统通过 Docker Compose 编排 PostgreSQL、Redis 和后端服务。

服务端 Linux/容器化环境 + Go 1.27/Gin + PostgreSQL 18 + Redis 7；客户端现代浏览器；开发期前端 Vite 开发服务器（5173）经 CORS 访问后端（8080）。Redis 与 PostgreSQL 均支持 Docker 容器化运行。

# 3．总体设计

## 3.0 AI 助手总体设计

AI 助手由 Vue Bottom Sheet、AI HTTP/SSE 适配层、上下文组装服务、OpenAI 兼容客户端和 PostgreSQL 会话仓储组成。上下文服务按 JWT 用户 ID 读取本人资料、信用、预约、候补和通知，并组合房间及座位数据；模型只生成简短文本或调用只读 `recommend_seats` 工具。工具结果经后端检查日期、时段、座位状态和实时占用后才作为卡片发送。最终预约由用户确认并复用预约服务，AI 无业务写权限。

接口包括 `GET/POST /api/ai/conversations`、`GET /api/ai/conversations/:id/messages`、`DELETE /api/ai/conversations/:id` 和 `POST /api/ai/chat/stream`。流式协议事件为 `meta`、`delta`、`card`、`done`、`error`。会话表与消息表按用户外键隔离，消息保留 OpenAI 的 `role/content/tool_calls/tool_call_id` 字段。

## 3.1 处理流程

系统总体处理流程为"请求—限流—认证—防重—业务—缓存/落库—调度闭环"：
1. 浏览器发起 HTTPS/HTTP 请求；
2. 接入层 Gin 路由与中间件链：CORS 处理 → 限流中间件（基于 Redis 限制敏感接口频次）→ JWT 认证（含 Redis 黑名单校验）→ RBAC 权限判定；
3. handler 解析与校验参数；
4. service 执行业务规则：
   - 读请求优先通过 `rediscache` 检索 Redis 旁路缓存，命中则极速返回；未命中时查库并防雪崩（随机 TTL）回填；
   - 预约/释放等高并发写请求，优先通过 `redissync` 获取分布式细粒度互斥锁（如 `lock:seat:<id>:<date>`），防止并发超卖，并执行数据库事务；事务提交后主动失效相关房间和统计缓存；
5. repository 参数化访问 PostgreSQL 18，依赖 GiST 排除约束最终兜底；
6. 统一格式返回响应；同时后台调度器通过 Redis 分布式锁完成主备选举，周期运行违约扫描、候补递补与签到提醒。

# 4．接口设计

## 4.1 外部接口

**（1）用户界面接口**：前端 SPA 通过 axios 调用后端 REST API；除登录/注册与健康检查外，全部请求携带 `Authorization: Bearer <JWT>`；响应统一为 `{"code", "message", "data"}`。

**（2）软件接口（REST API 分组）**：

| 分组 | 前缀 | 主要端点 | 缓存/限流策略 |
| --- | --- | --- | --- |
| 认证 | /api/auth | register、login、logout、profile | login 接口受限流（每 IP 每分钟 10 次）；logout 写入 JWT 黑名单 |
| 房间座位 | /api/rooms、/api/seats | 房间列表、座位平面图（含时段占用） | 房间详情及房间列表采用 Redis 缓存；座位平面图按目标时段直接查询 PostgreSQL |
| 预约 | /api/reservations | 创建、自动分配、签到、离开、返回、签退、取消、我的预约 | 手动预约和自动分配分别受限流（每用户每秒 2 次）；加分布式锁并失效对应房间缓存 |
| 候补 | /api/waitlist | 加入、取消、我的候补 | 状态流转保障 |
| 通知 | /api/notifications | 列表、未读数、标记已读、全部已读 | - |
| 统计 | /api/stats | heatmap、overview、trend、peak、top-seats | 耗时聚合指标采用 Redis 旁路缓存（TTL 3 分钟并带 ±10% 抖动） |
| AI 助手 | /api/ai | conversations 列表/新建/消息/删除、chat/stream | 仅 student 角色；chat/stream 每用户每分钟 10 次限流；SSE 事件 meta/delta/card/done/error |
| 管理端 | /api/admin | 房间 CRUD、座位 CRUD/批量生成、用户管理 | 房间或座位写操作主动使 Redis 关联缓存失效 |

**（3）硬件接口**：无。

## 4.2 内部接口

后端各 service 间通过 Go 接口解耦，关键内部接口约定：

| 提供方 | 接口方法（摘要） | 调用方 |
| --- | --- | --- |
| AuthService | Register / Login / Logout / IsTokenBlacklisted / Profile | auth handler、jwt 中间件 |
| SeatService | ListRooms / GetSeatMap / CreateRoom / BatchGenSeats / UpdateSeat / DeleteSeat | 对应 handler、allocation |
| ReservationService | Create / AutoAllocate / Checkin / Leave / Return / Checkout / Cancel / ListMine | 对应 handler、scheduler |
| CreditService | ApplyViolation / ApplyCompletion / ApplyLateCancel / GetCredit | reservation、scheduler、handler |
| WaitlistService | Join / Cancel / ListMine / PromoteReleased | handler、scheduler |
| NotificationService | Push / List / MarkRead | 各业务 service、handler |
| StatsService | Heatmap / Overview / Trend / Peak / TopSeats | handler |
| AIService | ListConversations / CreateConversation / DeleteConversation / ListMessages / Chat | ai handler |
| AIClient | Stream（OpenAI 兼容 SSE + 工具调用） | AIService |
| RedisSync | TryLock / Unlock | reservation、scheduler |
| RedisCache | Get / Set / Del / DelPrefix | seat、stats、reservation |

跨模块协作事件约定：预约取消/违约 → 触发候补递补；递补成功 → 触发通知与预约创建；数据变更时主动失效 Redis 对应键前缀。

# 6．运行设计

## 6.1 运行模块的组合

启动组合：`cmd/server` → 加载配置 → 建立 PostgreSQL 连接池 → 建立 Redis 客户端连接池（连通性自检） → 装配 repository → 装配 service（注入 Cache 与 Lock 组件） → 注册路由与限流中间件 → 启动 HTTP 监听 → 启动调度器 goroutine（带主备选举机制）。

运行期并发组合：每个 HTTP 请求一个 goroutine（Gin 管理）；调度器独立 goroutine，每 60 秒执行一轮（基于 Redis 锁竞选 Leader → 违约扫描 → 候补递补 → 签到提醒）。

## 6.2 运行控制

- 配置通过环境变量注入（STUDYROOM_PORT / STUDYROOM_DB_URL / STUDYROOM_JWT_SECRET / STUDYROOM_REDIS_ADDR / STUDYROOM_REDIS_PASSWORD / STUDYROOM_REDIS_DB，以及 AI 相关的 STUDYROOM_AI_BASE_URL / AI_API_KEY / AI_MODEL / AI_CONNECT_TIMEOUT_SECONDS / AI_RESPONSE_TIMEOUT_SECONDS / AI_CONTEXT_MESSAGES）；
- 统一在仓库根目录 `.env` 维护（模板 `.env.example`），后端启动时自动读取，Docker Compose 亦读取同一文件；
- `/api/health` 暴露存活状态（含 PostgreSQL 数据库连通性）；
- 收到 SIGINT/SIGTERM 优雅关闭：停止调度器 → 关闭 HTTP → 释放 Redis 连接 → 释放数据库连接池。

## 6.3 运行时间

调度周期为 60 秒。其他接口响应时间和吞吐能力需在目标部署环境通过专项性能测试确认，本说明书不记录未经复测的数值。

# 7．出错处理设计

## 7.1 出错输出信息

统一响应 `{code, message, data}`；HTTP 状态码与业务场景映射：

| HTTP | 场景 | message 示例 |
| --- | --- | --- |
| 400 | 参数错误 | 开始时间必须早于结束时间 |
| 401 | 未认证/令牌已注销/过期 | 令牌无效、已注销或已过期 |
| 403 | 无权限/禁约/禁用 | 信用分过低，暂时禁止预约 |
| 404 | 资源不存在 | 座位不存在 |
| 409 | 冲突/并发争抢 | 该座位此时段已被预约，或正在被他人预约，请稍后重试 |
| 429 | 频次超限 | 请求过于频繁，请稍后再试 |
| 500 | 内部错误 | 服务内部错误，请稍后重试 |

## 7.2 出错处理对策

1. **事务回滚**：预约创建+信用变动等多表写操作置于同一数据库事务，失败整体回滚；
2. **约束兜底**：分布式互斥锁先行排队并发请求，数据库排除约束最终兜底（409 语义转换）；
3. **Redis 优雅降级（Fallback）**：
   - 启动期如未配置 Redis 或 Redis 宕机，系统自动切换为纯数据库降级模式，并在日志中输出警告，不中断核心业务；
   - 运行期若 Redis 发生瞬时故障，缓存读取失败时相关服务回源数据库；预约锁获取发生 Redis 错误时记录日志并依赖 PostgreSQL 排除约束兜底；认证黑名单查询错误时记录日志并继续校验后的请求；注销操作因无法写入黑名单而返回 503；调度器运行中无法取得 Redis 选主锁时跳过本轮；
4. **降级运行**：统计接口异常不影响预约主链路；通知写入失败仅记日志不阻断主流程；
5. **恢复与再启动**：服务无本地状态，重启即恢复；调度任务幂等（状态条件更新），重复执行无副作用。

# 8．安全保密设计

1. 口令 bcrypt（cost=10）存储，杜绝明文/可逆加密；
2. JWT HS256，密钥经环境变量注入，令牌含 uid/role/过期时间，有效期 24h；
3. JWT 主动注销黑名单：用户退出登录或被封禁时，将 Token 哈希存入 Redis 并设置等于 Token 剩余有效期的 TTL，中间件实时校验，彻底解决 JWT 无法提前作废的安全缺陷；
4. 接口级防刷与限流：敏感端点（如登录、提交预约）挂载 Redis 计数器/滑动窗口中间件，超过阈值直接阻断（429 Too Many Requests），防范暴力破解与恶意抢座；
5. RBAC：`/api/admin/**` 强制 admin 角色，中间件统一拦截；
6. SQL 全参数化（pgx 占位符），杜绝字符串拼接；
7. 日志脱敏：口令字段永不落日志；
8. 开发配置允许任意来源跨域，正式部署前需配置来源白名单。

# 9．维护设计

1. **数据库演进**：backend/migrations 按序号管理，`scripts/apply_migrations.sh` 可重复执行；
2. **结构化日志**：Gin 访问日志 + 业务错误日志，含 trace 摘要；
3. **单元测试**：核心算法（分配/状态机/信用/冲突）单测覆盖，CI 自动执行；
4. **配置集中**：全部环境变量集中在 config 包，变更零散参数无需改代码；
5. **部署脚本**：scripts 目录提供集群初始化/启停、迁移、种子脚本，降低环境维护成本。
