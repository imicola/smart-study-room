## 1 说明

### 1.1 编写目的

### 1.2 缺陷分级定义

| 级别 | 名称 | 判定标准 | 处理要求 |
| --- | --- | --- | --- |
| A | 致命 | 导致系统崩溃、数据错误、安全漏洞或核心功能不可用 | 必须修复后方可交付 |
| B | 严重 | 主要功能异常或存在明显安全隐患 | 必须修复或给出明确缓解措施 |

`已修复` / `已缓解（设计约束）` / `待修复` / `已知限制（不修复）`

### 1.4 统计口径说明

本报告的缺陷来源包括：自动化测试的失败/告警输出、代码审查结论、构建告警。**不包含无法复现或未经核实的问题**。

## 3 缺陷明细

### BUG-001 CORS 允许任意来源（B 严重）

| 项目 | 内容 |
| --- | --- |
| 发现阶段 | 代码审查 |
| 发现人 | 王建东（nightsky5819） |
| 模块 | `backend/internal/middleware/cors.go` |
| 描述 | 中间件固定返回 `Access-Control-Allow-Origin: *`，任意站点均可携带用户 Token 发起跨域请求。 |
| 复现 | 审查 `cors.go` 第 13 行：`c.Header("Access-Control-Allow-Origin", "*")`。 |
| 影响 | 教学演示环境可接受；若对外部署，存在被第三方站点滥用会话的风险。 |
| 处理 | **已缓解（设计约束）**：开发期便于前端 5173 联调，刻意保留。已在《需求规格说明书》7.1 与《概要设计》第 8 章明确"正式部署前应收紧为可信来源白名单"。 |
| 建议修复 | 将允许来源改为 `.env` 注入的白名单，生产环境默认拒绝未列出来源。 |

### BUG-002 JWT 黑名单查询失败时降级放行（B 严重）

| 项目 | 内容 |
| --- | --- |
| 发现阶段 | 代码审查 |
| 发现人 | 王建东（nightsky5819） |
| 模块 | `backend/internal/middleware/auth.go` |
| 描述 | 校验令牌时若 Redis 黑名单查询出错，仅记录日志并继续放行请求（第 34—37 行），意味着 Redis 故障期间已注销的令牌可能仍被接受。 |
| 复现 | 关闭 Redis 后，用已登出令牌访问受保护接口。 |
| 影响 | 可用性与安全性的取舍：避免 Redis 抖动导致全站鉴权失败，代价是短时注销不生效。 |
| 处理 | **已缓解（设计约束）**：属有意的降级策略，日志留有告警。已在测试用例 TC-U03 中覆盖"黑名单读取失败被上报"。 |
| 建议修复 | 引入本地短期缓存或让 `logout` 失败时返回 503 并提示用户重试；对高风险接口可配置为"查询失败即拒绝"。 |

### BUG-003 前端产物体积告警（C 一般）

| 项目 | 内容 |
| --- | --- |
| 发现阶段 | 前端构建（`npm run build`） |
| 发现人 | 王建东（nightsky5819） |

### BUG-004 测试脚本目标端口与实际部署不一致（C 一般）

| 项目 | 内容 |
| --- | --- |
| 发现阶段 | 集成测试执行准备 |
| 发现人 | 王建东（nightsky5819） |
| 模块 | `scripts/test_api_e2e.py`、`scripts/test_concurrency.py` |
| 描述 | 两个脚本中 `BASE_URL` 硬编码为 `http://localhost:8095/api`，而 Docker Compose 默认将后端映射到宿主机 8080。端口不一致时全部用例连接失败。 |
| 复现 | 以默认 `docker compose up -d` 启动后端后直接运行脚本。 |
| 影响 | 影响测试可重复性，易造成"用例全红"的误判。 |
| 处理 | **已知限制（不修复）**：已在《测试计划》第 4.2 节与《系统测试报告》中明确提示"执行前需按实际端口修正 `BASE_URL`"。 |
| 建议修复 | 改为读取环境变量 `BASE_URL`，默认回落到 8080。 |

## 4 缺陷分布分析

### 4.1 按模块分布

| 模块 | 缺陷数 | 说明 |
| --- | --- | --- |
| 安全与中间件 | 2 | CORS 策略、黑名单降级 |
| 前端 | 1 | 产物体积 |
| 测试工具链 | 2 | 端口硬编码、密钥硬编码 |
| 文档 | 3 | 重复段落、署名不一致、角色口径 |
| 核心业务逻辑 | 0 | 预约、分配、生命周期、候补等模块未发现缺陷 |

### 4.2 结论

1. **核心业务路径无缺陷**：单元测试与 23 项端到端用例全部通过，并发抢座实现"1 成功 / 19 冲突 / 0 超卖"，说明预约与并发互斥逻辑达到设计预期；
2. **主要风险集中在部署加固**：CORS 与黑名单降级属有意的工程取舍，已在文档中明确披露；
3. **文档一致性是主要问题来源**：占缺陷总数 37.5%，已随本轮文档复核全部修复；
4. **无语料支撑的功能缺失**：AI 助手、3D 选座等扩展能力未出现功能性缺陷记录。
