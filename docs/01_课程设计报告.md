# 1 系统概述

## 1.1 现状描述

随着考研、考证与终身学习需求的增长，高校图书馆与付费自习室面临持续的"一座难求"。对某高校图书馆的实地调研与访谈显示，传统自习室管理存在五个突出问题：

1. **信息不透明**：学生无法提前获知空位分布，"到馆找座"平均耗时 10 分钟以上，高峰期更甚；
2. **占座严重**：以物品占座造成"名义占用、实际闲置"，真实利用率被进一步压低；
3. **爽约无成本**：口头预约或简单登记后不到场无任何约束，座位被无效锁定整个时段；
4. **管理粗放**：管理员缺乏数据支撑，无法量化各时段、各区域的利用情况，排班与开放决策凭经验；
5. **分配低效**：高峰期人工引导排队秩序混乱，体验差且易生纠纷。

## 1.2 系统目标

本系统定位为"面向共享自习室的一站式座位预约与运营平台"，总目标是将座位资源**在线化、公平化、数据化**。分解为七个可度量目标（G1~G7）：在线预约、智能分配、全生命周期管理、信用治理、满座候补、数据可视化、消息通知（详见《需求规格说明书》2.1 节）。

## 1.3 系统开发方法

- **分析与设计方法**：面向对象分析与设计（OOA/OOD），以用例驱动需求、以领域模型驱动设计，产出用例图、类图、ER 图、状态图、时序图、数据流图等全套 UML/结构化模型；
- **过程模型**：增量模型。按"基础设施 → 认证 → 资源管理 → 预约核心 → 智能分配 → 治理机制（信用/候补/通知）→ 统计分析 → 前端集成"的顺序分八个增量交付，每个增量均可运行、可验证；
- **工程实践**：Git 分支协作（feature 分支 + 组长审查合并）、GitHub Actions 持续集成、表驱动单元测试、迁移脚本管理数据库演进。

# 3 系统设计

## 3.1 模块结构设计

系统采用前后端分离的多层架构，整合关系型数据库持久化与高性能内存中间件：客户端层（Vue 3 SPA）→ 接入层（Gin 路由 + RateLimit 限流 + JWT 认证与黑名单 + RBAC 中间件链）→ 业务服务层（9 个 service + 分布式调度器）→ 缓存与互斥协调层（Redis 7 旁路缓存 + 分布式互斥锁）→ 数据持久化层（PostgreSQL 18 强一致性与 GiST 排除约束）。

【插图位置：diagrams/02_系统架构图.mmd —— 图 3-1 系统架构图】

【插图位置：diagrams/10_模块结构图.mmd —— 图 3-2 后端模块结构图】

后端包结构与模块职责：
- `internal/handler`：HTTP 协议适配、参数解析与统一响应；
- `internal/service`：核心业务逻辑、冲突检测、评分算法、状态机流转与缓存/加锁协调；
- `internal/repository`：PostgreSQL 数据访问（pgx 连接池）与 Redis 客户端连接池管理；
- `internal/pkg/redissync`：基于 Redis Lua 脚本的分布式互斥锁（支持抢座并发控制与调度器 Leader 选举）；
- `internal/pkg/rediscache`：旁路缓存通用封装（Cache-Aside、随机 TTL 防雪崩、Redis 宕机优雅降级）；
- `internal/middleware`：CORS、JWT 认证、Redis 黑名单校验与 API 频次限流中间件；
- `internal/model`：领域实体与 DTO 模型定义；
- `internal/service/scheduler.go`：分布式高可用周期任务调度器；
- `cmd/server`：服务装配与依赖注入入口。

模块间依赖单向，跨模块协作通过接口解耦。Redis 启动连接失败时系统以 PostgreSQL 运行；运行期故障策略按缓存、预约锁、认证注销与调度器用途分别处理。

## 3.5 算法设计

**自动分配评分模型**（完整流程图如下）：

【插图位置：diagrams/14_自动分配算法流程图.mmd —— 图 3-11 自动分配算法流程图】

> 总分 = 偏好匹配分（区域 30 + 电源 25 + 靠窗 15）− 近 7 日利用率 × 20 + 随机扰动 (0,1)

设计意图：偏好项保证个性化匹配；**热度均衡因子**将人流分散到低使用率座位，削峰填谷，提升整体资源利用均衡度；微扰避免所有人涌向同一"最优"座位。评分函数实现为无副作用纯函数（ScoreCandidates），可直接单元测试。

**热力图聚合算法**：generate_series 按房间开放时间生成与查询日期对齐的小时轴，对每个"座位×小时"格子以 EXISTS + tsrange 重叠判定占用，Go 侧组装矩阵并计算小时利用率（见详细设计 3.9 与图 3-12）。

# 1．引言

## 1.1 编写目的

为明确"智能共享自习室预约系统"的软件需求、安排项目规划与进度、组织软件开发与测试，特编写本需求规格说明书。

## 1.2 项目背景

a. **委托单位、开发单位与主管部门**：本项目为《系统分析与设计》课程设计课题，由课程设计小组（5 人）自主选题、自主开发，指导教师所在课程组为业务主管部门。

b. **系统与其他系统的关系**：本系统为独立 B/S 架构 Web 应用，不依赖外部业务系统；对外仅依赖标准网络与浏览器环境。系统面向高校共享自习室场景，向前来自习的学生提供座位查询、预约、签到等服务，向管理员提供座位资源管理与运营统计服务。

**现状与问题**：调研发现，传统自习室管理存在以下痛点——

1. **信息不透明**：学生无法提前得知自习室空位情况，往返奔波"找座"时间成本高；
2. **占座严重**：物品占座导致座位名义占用、实际闲置，资源利用率低；
3. **爽约无成本**：预约后不到场没有任何约束，座位被无效锁定；
4. **管理粗放**：管理员缺乏数据支撑，无法量化了解各时段、各区域的座位利用情况；
5. **分配低效**：高峰期人工引导分配座位秩序混乱，体验差。

本系统通过"在线选座 + 智能分配 + 信用治理 + 数据可视化"四位一体的方案解决上述问题。

排除约束（数据库层兜底，双保险）：

- `excl_seat_overlap`：同一座位同一天的**活跃预约**时段不得重叠；
- `excl_user_overlap`：同一用户同一天的**活跃预约**时段不得重叠（防止一人多占）。

**（7）notifications 通知表**：id、user_id、type（六类事件枚举）、title、content、is_read、created_at。

**（8）ai_conversations AI 会话表**：id、user_id（外键→users，级联删除）、title（默认"新对话"）、created_at、updated_at。

**（9）ai_messages AI 消息表**：id、conversation_id（外键→ai_conversations，级联删除）、role（system/user/assistant/tool）、content、tool_calls（JSONB）、tool_call_id、status（streaming/complete/failed）、created_at。

2. **用户注册采集**：注册时采集用户名、口令（哈希）、姓名、学号；
3. **行为自动记录**：预约创建、签到、签退、取消等操作由系统自动写入对应表并维护时间戳；
4. **调度器采集**：后台定时任务扫描超时未签到预约，自动产生违约记录与信用流水；
5. **统计聚合**：热力图与统计报表由历史预约数据按"座位 × 小时"聚合生成，无需人工上报。

# 7．其它需求

## 7.1 安全保密

1. 口令仅存 bcrypt 哈希（cost=10），任何接口/日志不得出现明文口令；
2. 会话采用 JWT（HS256，24 小时有效），签名密钥环境变量注入；
3. RBAC：管理端接口仅 admin 角色可访问；
4. 全部 SQL 采用参数化查询，防 SQL 注入；前端输入做长度与格式校验，防 XSS；
5. 当前开发配置允许任意来源，正式部署前应收紧为可信来源白名单。

## 7.2 可维护性

1. 后端按 handler / service / repository 三层组织，模块边界清晰；
2. 数据库变更通过迁移脚本管理，可重复执行；
3. 关键业务（分配算法、状态机、信用规则）配套单元测试；
4. 统一结构化日志，便于排障。

## 7.3 可移植性

1. 后端为静态编译的 Go 程序，可部署于任意 Linux 环境，具备容器化条件；
2. 数据库采用标准 SQL 与 PostgreSQL 特性（排除约束），迁移成本可控；
3. 前端构建产物为静态资源，可由任意 Web 服务器托管。

## 7.4 可使用性

1. 座位平面图直观呈现占用状态，预约操作 ≤ 3 步；
2. 自动分配提供推荐理由，增强可解释性与信任感；
3. 关键结果（预约成功、违约、递补）均有即时消息反馈。

# 3．总体设计

## 3.1 处理流程

系统总体处理流程为"请求—限流—认证—防重—业务—缓存/落库—调度闭环"：
1. 浏览器发起 HTTPS/HTTP 请求；
2. 接入层 Gin 路由与中间件链：CORS 处理 → 限流中间件（基于 Redis 限制敏感接口频次）→ JWT 认证（含 Redis 黑名单校验）→ RBAC 权限判定；
3. handler 解析与校验参数；
4. service 执行业务规则：
   - 读请求优先通过 `rediscache` 检索 Redis 旁路缓存，命中则极速返回；未命中时查库并防雪崩（随机 TTL）回填；
   - 预约/释放等高并发写请求，优先通过 `redissync` 获取分布式细粒度互斥锁（如 `lock:seat:<id>:<date>`），防止并发超卖，并执行数据库事务；事务提交后主动失效相关房间和统计缓存；
5. repository 参数化访问 PostgreSQL 18，依赖 GiST 排除约束最终兜底；
6. 统一格式返回响应；同时后台调度器通过 Redis 分布式锁完成主备选举，周期运行违约扫描、候补递补与签到提醒。

# 6．运行设计

## 6.1 运行模块的组合

启动组合：`cmd/server` → 加载配置 → 建立 PostgreSQL 连接池 → 建立 Redis 客户端连接池（连通性自检） → 装配 repository → 装配 service（注入 Cache 与 Lock 组件） → 注册路由与限流中间件 → 启动 HTTP 监听 → 启动调度器 goroutine（带主备选举机制）。

运行期并发组合：每个 HTTP 请求一个 goroutine（Gin 管理）；调度器独立 goroutine，每 60 秒执行一轮（基于 Redis 锁竞选 Leader → 违约扫描 → 候补递补 → 签到提醒）。

## 6.2 运行控制

- 配置通过环境变量注入（STUDYROOM_PORT / STUDYROOM_DB_URL / STUDYROOM_JWT_SECRET / STUDYROOM_REDIS_ADDR / STUDYROOM_REDIS_PASSWORD / STUDYROOM_REDIS_DB）；
- `/api/health` 暴露存活状态（含 PostgreSQL 数据库连通性）；
- 收到 SIGINT/SIGTERM 优雅关闭：停止调度器 → 关闭 HTTP → 释放 Redis 连接 → 释放数据库连接池。

## 6.3 运行时间

调度周期为 60 秒。其他接口响应时间和吞吐能力需在目标部署环境通过专项性能测试确认，本说明书不记录未经复测的数值。

# 7．出错处理设计

## 7.1 出错输出信息

统一响应 `{code, message, data}`；HTTP 状态码与业务场景映射：

| HTTP | 场景 | message 示例 |
| --- | --- | --- |
| 400 | 参数错误 | 开始时间必须早于结束时间 |
| 401 | 未认证/令牌已注销/过期 | 令牌无效、已注销或已过期 |
| 403 | 无权限/禁约/禁用 | 信用分过低，暂时禁止预约 |
| 404 | 资源不存在 | 座位不存在 |
| 409 | 冲突/并发争抢 | 该座位此时段已被预约，或正在被他人预约，请稍后重试 |
| 429 | 频次超限 | 请求过于频繁，请稍后再试 |
| 500 | 内部错误 | 服务内部错误，请稍后重试 |

## 7.2 出错处理对策

1. **事务回滚**：预约创建+信用变动等多表写操作置于同一数据库事务，失败整体回滚；
2. **约束兜底**：分布式互斥锁先行排队并发请求，数据库排除约束最终兜底（409 语义转换）；
3. **Redis 优雅降级（Fallback）**：
   - 启动期如未配置 Redis 或 Redis 宕机，系统自动切换为纯数据库降级模式，并在日志中输出警告，不中断核心业务；
   - 运行期若 Redis 发生瞬时故障，缓存读取失败时相关服务回源数据库；预约锁获取发生 Redis 错误时记录日志并依赖 PostgreSQL 排除约束兜底；认证黑名单查询错误时记录日志并继续校验后的请求；注销操作因无法写入黑名单而返回 503；调度器运行中无法取得 Redis 选主锁时跳过本轮；
4. **降级运行**：统计接口异常不影响预约主链路；通知写入失败仅记日志不阻断主流程；
5. **恢复与再启动**：服务无本地状态，重启即恢复；调度任务幂等（状态条件更新），重复执行无副作用。

# 8．安全保密设计

1. 口令 bcrypt（cost=10）存储，杜绝明文/可逆加密；
2. JWT HS256，密钥经环境变量注入，令牌含 uid/role/过期时间，有效期 24h；
3. JWT 主动注销黑名单：用户退出登录或被封禁时，将 Token 哈希存入 Redis 并设置等于 Token 剩余有效期的 TTL，中间件实时校验，彻底解决 JWT 无法提前作废的安全缺陷；
4. 接口级防刷与限流：敏感端点（如登录、提交预约）挂载 Redis 计数器/滑动窗口中间件，超过阈值直接阻断（429 Too Many Requests），防范暴力破解与恶意抢座；
5. RBAC：`/api/admin/**` 强制 admin 角色，中间件统一拦截；
6. SQL 全参数化（pgx 占位符），杜绝字符串拼接；
7. 日志脱敏：口令字段永不落日志；
8. 开发配置允许任意来源跨域，正式部署前需配置来源白名单。

# 9．维护设计

1. **数据库演进**：backend/migrations 按序号管理，`scripts/apply_migrations.sh` 可重复执行；
2. **结构化日志**：Gin 访问日志 + 业务错误日志，含 trace 摘要；
3. **单元测试**：核心算法（分配/状态机/信用/冲突）单测覆盖，CI 自动执行；
4. **配置集中**：全部环境变量集中在 config 包，变更零散参数无需改代码；
5. **部署脚本**：scripts 目录提供集群初始化/启停、迁移、种子脚本，降低环境维护成本。

## 3.12 缓存与高并发协调架构（Redis 组件设计）

为了提升系统在高并发选座与热点查询场景下的吞吐能力并保障分布式一致性，系统新增独立的高性能内存协调层：

### 1. 分布式互斥锁组件（internal/pkg/redissync）
- **加锁实现**：基于 `redis.SetArgs{Mode: "NX", TTL: expire}` 命令。加锁时生成全局唯一的 UUID 作为 Token（Value）。若获取失败，直接返回不可重入互斥错误；
- **原子解锁**：采用 Lua 脚本比对 Token，确保仅有锁的持有者能够释放锁，杜绝因任务超时导致的误删他人锁问题：
  ```lua
  if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
  else
      return 0
  end
  ```
- **优雅降级**：当 Redis 客户端为 nil（未配置或离线降级）时，`TryLock` 自动放行返回虚拟解锁函数，确保系统在纯 PostgreSQL 模式下仍可继续工作。

### 2. 旁路缓存组件（internal/pkg/rediscache）
- **读取策略（Cache-Aside）**：先查 Redis。命中且反序列化成功则直接返回；未命中时触发 loader 回源查询数据库，并将结果以 JSON 格式写回 Redis；
- **防雪崩机制（Jitter）**：基础 TTL（如 5 分钟）额外叠加 `基础 TTL 的 ±10%` 随机抖动时间，打散同一批热点数据的过期时点；
- **主动失效**：数据发生变更（写操作）时，通过 `Delete` 或 `DeletePrefix` 立即剔除失效键，保证数据最终一致性。

### 3. API 频次限流中间件（internal/middleware/ratelimit.go）
- **算法模型**：固定窗口计数器模型。客户端发起请求时，以 `ratelimit:<prefix>:<identifier>` 为键执行 `INCR`；
- **原子初始化**：若计数器值为 1，则同时设置窗口过期时间（`EXPIRE window`）；
- **阻断控制**：若计数值超过上限，直接中断请求链并响应 HTTP 429 Too Many Requests，并输出规范的 `{"code": 429, "message": "请求过于频繁，请稍后再试"}`。

### 4. JWT 注销黑名单（internal/service/auth.go）
- 传统的无状态 JWT 无法提前注销。本系统在用户调用 `/api/auth/logout` 时，服务端解析 Token 的剩余生存时间（`exp - now`）；
- 将 Token 哈希值存入 Redis：`SET studyroom:auth:blacklist:<hash> "1" EX <remaining_seconds>`；
- `JWTMiddleware` 中间件在每次验证签名通过后，额外查询一次 Redis 黑名单，已注销的 Token 将被即时拦截，保障会话安全。
